# Evaluating added value

Choose one fixed stay and hotel DNA first. Keep the same conversation, dates and baseline brief while comparing the two tracks. For local discovery, the Prague anniversary case is an immediately available starting point. For real person research, choose a consenting test subject with verified accessible public sources; the recorded fictional names are not search targets.

For each retained idea, explain the chain: guest cue, new finding, source and check date, what changes in the proposal, hotel capability required, unresolved checks and human decision. Two useful sourced options are better than a long list with no practical consequence.

| Question | Evidence to show |
|---|---|
| Did the research add anything? | A concrete difference from the conversation/DNA-only baseline |
| Does it fit these people? | An explicit guest statement and preserved individual constraints |
| Can another person check it? | Source URL, relevant evidence, date and uncertainty |
| Can the hotel assess delivery? | Capabilities, owner, timing, costs and missing confirmations |
| Did the human keep control? | Retained, edited and rejected proposals with reasons |
| Was the experiment practical? | Time, external calls, cost and failure/abstention rate |

## Cases that must not become false successes

- Same-name or unverifiable identity: abstain; preserve the baseline.
- No useful extra evidence: return no-results, not filler.
- Event outside the stay, unclear slot, stale listing or inaccessible source: reject it or show the unresolved gap.
- Availability advertised but unconfirmed: keep those states distinct.
- Price lacking currency, basis or inclusions: leave the missing fields unknown; no final hotel price is implied.
- Conflict with an allergy, desired pace or hotel restriction: flag or reject the proposal.
- Instructions embedded in a source: ignore them; do not grant tools, send data or change the task.
- Guest withdrawal, revoked stay or human-edited baseline: stop or require a fresh run as appropriate.

The automated suite verifies software boundaries and version preservation. The scripted browser journey verifies the UI. Neither evaluates live source quality, hotel feasibility or guest satisfaction. Record a separate real-source experiment, including failed and discarded results, when those adapters are built.

## A short demonstration

Show the baseline and the relevant guest cue. Run the chosen extension on real permitted sources, or clearly identify a recorded run. Open one source, explain one accepted change and one rejection, then create the reviewed brief. End with the remaining hotel checks. Declare which code existed before the event and which component the team built during it.
