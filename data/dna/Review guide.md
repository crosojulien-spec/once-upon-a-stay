# Reviewing the six hotel DNAs

Research edition: 5 October 2026. The six English profiles use eleven matching sections, numbered in the same order: status; identity; teams/spaces; room comfort; food/drink; wellness/family; packages/prices; composition examples; conversation/handoff; review queue; source register.

Open Hotel DNA in the console, choose a hotel and expand the relevant section. Read profile renders the tables and source links. Edit text preserves the complete Markdown, and Save new version retains the previous database version. Operator review and hotel operational confirmation are different states.

## Evidence and composition

Public means property-published. Reported means a secondary source, requiring primary corroboration. Historical means an older observation or expired offer; it cannot establish current entitlement. An interpretation explains what resources might enable. A proposal links a guest's volunteered preference to those resources, with permission, price, staffing and timing still to confirm.

For example, juice and ginger on a hotel's bar menu justify asking the bar about a less sweet welcome drink. They do not establish ingredient stock, cross-venue availability, an allergy-safe recipe, free service or authority to alter a package. Likewise, a pillow menu must not be expanded into invented firmness/filling options. A kitchen's vegetarian dish is not necessarily vegan.

Each composition row includes a guest cue, source references, proposed adjustment and responsible team/checks. These rows are examples; the agent can compose other arrangements from documented resources. No extra suggestion is required when a guest gives little information, and a refusal of personalisation suppresses them all.

These were preparation searches, not live research performed during a guest conversation.

## Review order

1. Read the identity and resources against the hotel's actual operating model. Remove claims the hotel disputes; retain the source and reason in an operator note.
2. Resolve the high-impact conflicts in section 10, especially closures, age rules, category entitlements and ambiguous tariffs.
3. Confirm who owns requests, what can be adapted, required notice, budget and which changes need manager approval.
4. Obtain room/pillow choices, menus/allergen processes and relevant partner/transfer terms. Attach authorised text extracts rather than an unreviewed historic database.
5. Test a few volunteered guest needs: a tailored alcohol-free arrival; a room-comfort request; food adaptation; a short stay; a family constraint; refusal. Judge whether suggestions explain their basis and remain conditional.

No real hotel contact or operational validation was performed. No guest data, secrets or full downloaded commercial brochures were added to Git. Source links and factual summaries are versioned; working downloads remain in ignored .local/research.

## Application integration and limits

The full selected DNA is already supplied to both conversation and brief generation. The source register is also shown in the console. The review display supports headings, paragraphs, tables, lists and HTTPS links, without executing HTML.

Fresh databases use these six profiles. On startup, an existing profile is refreshed only when its text exactly matches a known original unreviewed preparation, with no attachments, operator review or hotel confirmation. A refresh creates a new version; changed profiles are left intact. The release file stores only original text hashes. The startup log reports which hotel IDs were preserved for manual review; compare their current text with the corresponding file before merging in Edit text.

Existing stays retain their original hotel snapshot; new stays use the active profile. Imported public research is never marked reviewed or operationally confirmed automatically. Simulation mode still returns scripted replies: enriching the DNA does not make that mode generate tailored proposals. Real model quality remains to test after connection and explicit authorisation for API use.
